# BUILD SPEC — T3.6 Hero power-on choreography

Board-bring-up entrance for the hero, pure CSS, ≤ 900 ms, coordinated with the first-visit boot overlay via a pre-paint `html.boot-hold` class. Absorbs and deletes the JS lead-underline block in `Layout.astro`.

---

## 1. Mechanism decision: CSS **animations** (fill `both`), NOT `@starting-style` + transitions

Argued, per the task:

1. **Pausability is the decider.** The boot overlay dismisses at a *variable* time (skip click, Escape, 1300 ms timeout, 700 ms safety net). A transition cannot be paused or held mid-flight; `transition-delay` is fixed at style resolution. An animation parks cleanly under `animation-play-state: paused` and resumes the full choreography the instant a class is removed. `@starting-style` transitions would fire at first style resolution — i.e. entirely behind the opaque overlay, which is the exact bug being fixed.
2. **No fights with component transition lists** (the same B2 rationale the reveal system already documents at `global.css:94-96`). `.hero__ctas` contains `.btn` (magnetic-follow transform transition) and `.hero__lead em::after` owns a transform. Entrance-as-transition on these would require merging transition lists; entrance-as-animation is orthogonal.
3. **Fail-open resilience.** The hidden state lives *only* in the animation's backwards fill. Base styles are the final state. Any context that strips animations — reduced motion, the print block's `animation: none !important`, exotic UAs — renders the hero fully visible. A base `opacity: 0` + transition design fails closed (invisible content), which would threaten D-006.
4. **Reduced motion is already handled by the house rule.** The global RM rule zeroes `animation-duration` and `animation-delay`; with fill `both` every entrance jumps to its end state. These are time-driven (not `animation-timeline`) animations, so no scroll-driven RM caveat applies — explicit `animation: none` overrides are still added as belt (§5).
5. **No `@supports` guard needed.** `@keyframes` + `animation-play-state` are universal; `@starting-style` would have required a guard and a static fallback path.

Hero elements stay **out of** the `.reveal`/`.fade` system, as today. Rationale: reveal is IO-driven, gated on `html.js.reveal-ready`, and staggered per viewport entry — the hero must animate exactly once, at load, *without* JS, and must be pausable by the boot hold. Mixing the two would double-animate and reintroduce a JS dependency. The reveal IO query (`.reveal, .fade, .section-head, .trace-div, .cert`) matches nothing in the hero; keep it that way.

## 2. Timeline (bring-up order, 80 ms beat grid, 60 ms underline stagger)

Beat step is `calc(var(--po) * 80ms)`; underline stagger reuses the house 60 ms stagger (same as the reveal `--i` step). Durations and easings are tokens only: `--t` 240 ms, `--t-slow` 520 ms, `--ease-out`. Keyframes are reused (`fade-in`, `rise-in`, `draw-underline`) — no new keyframes.

| # | Element | `--po` | Start | Keyframes | Duration | Ends |
|---|---|---|---|---|---|---|
| 1 | `.hero__eyebrow` (LED + label — power indicator) | 0 | 0 ms | `fade-in` | 240 ms | 240 |
| 2 | `h1` (name) | 1 | 80 ms | `rise-in` | 520 ms | 600 |
| 3 | `.hero__topmark` (IC topmark) | 3 | 240 ms | `fade-in` | 240 ms | 480 |
| 4 | `.hero__lead` | 4 | 320 ms | `rise-in` | 520 ms | 840 |
| 5 | lead `em::after` underlines ×4 | `--d`: 480/540/600/660 ms | | `draw-underline` | 240 ms each | 720/780/840/900 |
| 6 | `.hero__ctas` | 7 | 560 ms | `rise-in` | 240 ms | 800 |
| 7 | `.hero__spec` (spec card) | 8 | 640 ms | `rise-in` | 240 ms | 880 |

Total: **900 ms**. Notes: beat indices 2, 5, 6 are intentionally skipped (breathing room after the name; CTAs/spec land on later beats). Bring-up order is defined by *start* order; the last underline finishing at 900 ms after the spec card is deliberate — the cyan signal completing is the closing beat ("signal acquired"). Strict serial *completion* would bust the 1 s budget. `.hero__scroll` is excluded (viewport-bottom peripheral cue, outside the specified order; adding it would extend the tail).

### 3.3 `src/data/inline-scripts.ts` — two one-line additions to `bootScript`

The hold must exist before the hero's first paint; this script executes synchronously while parsing `<body>`'s first child, before the hero markup exists — guaranteed pre-paint. Critically, the class is added **after** the reduced-motion/seen early-return, so returning visitors and RM users never get held.

After the line `try { sessionStorage.setItem("rr_boot", "1"); } catch { /* the intro may simply repeat later */ }`, insert:

```js
  document.documentElement.classList.add("boot-hold");
```

Inside `finish()`, immediately after `boot.remove();`, insert:

```js
    document.documentElement.classList.remove("boot-hold");
```

Release happens in `finish()` (wipe *end*), not `dismiss()` (wipe *start*): the 320 ms wipe reveals bottom-up, so the eyebrow/name region is uncovered last — releasing at wipe-start would burn the first beats behind the still-opaque top band, the exact bug being fixed. With release at `finish()`, the wipe lands on page chrome + an unpowered hero, then the board brings up over 900 ms. `finish()` is the single funnel for both the `animationend` path and the 700 ms safety timeout, so one removal covers every dismissal route (skip, Escape, timeout, safety net).

CSP: no manual work. `Layout.astro` hashes the imported `bootScript` string (line 29) and `scripts/check-build.mjs` re-verifies against dist — the hash updates automatically with the edit.

**Delete** the now-dead lead-underline block (lines 173–179):

```ts
      // ---- Hero underline draw on load ----
      const hero = document.querySelector(".hero");
      if (hero) {
        const ems = hero.querySelectorAll(".hero__lead em");
        ems.forEach((em, i) => (em as HTMLElement).style.setProperty("--d", `${600 + i * 160}ms`));
```

**Add** in its place (bundled module, CSP-clean via `'self'`):

```ts
      // ---- Hero power-on hold: belt for the boot inline script ----
      // The hold is added/removed by bootScript; these guards cover a boot
      // that never activated (exotic failure) and bfcache restores where the
      // overlay was already gone when the page was frozen.
      const releaseHold = () => document.documentElement.classList.remove("boot-hold");
      if (!document.querySelector(".boot.is-active")) releaseHold();
      window.addEventListener("pageshow", (e) => {
        if (e.persisted && !document.querySelector(".boot.is-active")) releaseHold();
      });
```

(This module always runs after the boot inline script — it is a deferred module; the check is safe. When boot *is* legitimately active, the hold is left alone and `finish()` releases it.)

## 4. No-JS story

`boot-hold` requires JS to exist; without JS it is never added, the boot overlay stays `display: none` (existing behavior), and the choreography — being unconditional CSS, *not* gated on `html.js` — plays fully at first paint. Content is never JS-dependent: it animates opacity/transform only, is present in the DOM from parse, and every no-animation fallback path lands on visible final-state base styles. D-006 upgraded, not just preserved.

## 5. Reduced motion

Instant, no sequence (§3.2c). Boot never shows (existing early return). Mid-session RM toggle during the choreography: the global RM rule zeroes durations/delays → all entrances jump to their fill-`both` end state immediately; the explicit `animation: none` in the RM block makes the same guarantee even while `boot-hold` is present.

## 6. Accessibility

- Opacity-hidden elements remain in the accessibility tree (opacity, unlike `visibility`/`display`, does not remove content), so screen readers see the full hero from parse regardless of choreography or hold state. During the boot overlay the page is already `inert` (existing behavior) — hold and inert are lifted in the same `finish()` call.
- No ARIA changes; the `h1` accessible name path (`.sr-only` + `aria-hidden` visual) is untouched.
- Focus behavior unchanged.
- Forced-colors: opacity/transform animations run harmlessly; no gradient/`background-clip` involvement.

## 7. Edge cases

| Case | Behavior |
|---|---|
| First visit, boot plays to 1300 ms timeout | Hold added pre-paint → hero parked hidden behind opaque overlay → wipe (320 ms) → `finish()` releases → 900 ms bring-up on the revealed page. |
| Skip / Escape at any time | Same funnel: `dismiss()` → wipe → `finish()` → release. |
| `animationend` never fires (background tab, animations off) | Existing 700 ms safety `setTimeout(finish)` also releases the hold. |
| Returning visitor (session-gated) or RM user | Boot script early-returns *before* adding the hold; choreography plays at first paint (instant under RM). |
| sessionStorage blocked | Unchanged from today (boot may repeat); hold add/remove path identical. |
| Late load / slow network | Irrelevant: the choreography is parse-time CSS on above-the-fold content — it plays whenever first paint happens, unlike the IO-reveal system there is no "already painted" replay hazard. Reload mid-scroll (scroll restoration) animates the hero off-screen to completion; harmless. |
| bfcache restore | Finished animations stay finished (fill `both` end state) — no replay, no flash. If the page was somehow frozen with a stale `boot-hold` and no active boot, the `pageshow` guard (§3.4) releases it. |
| Boot script throws between hold-add and `finish` | The bundled-module belt (`if (!document.querySelector(".boot.is-active")) releaseHold()`) covers a boot that never activated; if the overlay is active-but-wedged the page is unusable behind it anyway (pre-existing failure class, unchanged). |
| Print | Print block strips animations; base styles are final state → complete hero, underlines drawn. |
| Constellation canvas / name scramble | Both already gate on `rr:boot-done`, which `finish()` dispatches after releasing the hold — canvas powers on with the choreography; scramble overlaps the h1 rise (§3.1). |
